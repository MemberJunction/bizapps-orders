Recognition is built at post time rather than staged at booking (D92 §8). `RevenueRecognitionDriver` gains `EarnedThrough(context, asOf)` — the cumulative sum of its own schedule's slices dated on or before a day — and confirm stops writing forward-dated release entries for deferred, time-driven lines. New operation `Orders.PostDueRecognition { AsOf, Preview?, OrderHeaderID? }` asks each confirmed line's driver what is earned through the date and posts the difference from the line's `RecognizedToDate` under rule 2, advancing the total in the same transaction as the entry; one transaction per line, so a line that fails is reported with its reason and the pass continues. Cumulative, so a back-dated term or a missed month catches up in one pass and a second run for the same date posts nothing. An `Orders: Post Due Recognition` Action and a monthly scheduled job at 02:30 UTC on the 1st run it ahead of accounting's 03:00 sweep, which is unchanged. The job ships **disabled**: the argument for shipping it live — that removing the staging makes a disabled job silently recognise nothing — holds only on a database that has never staged. A deferred line confirmed before cutover already has its staged entries while its `RecognizedToDate` reads 0, so the first cumulative pass would recognise it twice. Enabling it requires a one-time reconciliation first. This reverses D14's "the whole obligation is visible in the ledger the day the order is confirmed"; the `RevenueRecognition` journal entry type's description is updated to say so.
